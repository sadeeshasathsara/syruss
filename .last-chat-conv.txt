Production middleware platforms (Stripe-style APIs, Workato, MuleSoft, the document-AI vendors) all follow the same shape. The credential tells the system who is sending, and nothing important is trusted from the request itself. Delivery is built to survive failures. Systems in the middle are connected through configured connections and mappings rather than custom code per customer.

Receiving documents securely
Tenancy comes from the credential, never from the payload. The sender can’t say “this is for workspace X”. The key is looked up, and the key row carries tenant, workspace and channel. Everything downstream (storage path, queue event, agent token) carries those IDs.

Channels. Each workspace gets named intake channels, such as “Supplier invoices” or “Warehouse scanner”. Each channel has its own key, allowed file types and size, whether to process automatically, and a source label. Every document then knows which workspace and which channel it came from.

Ways documents arrive. Real platforms offer several, with REST first:

REST upload: POST /v1/intake/{channel} with multipart for small files, or a presigned-URL flow for big ones (request an upload URL, PUT straight to object storage, then call “complete”).
Email-in: a per-channel address with a sender allowlist and SPF/DKIM checks. This is how most real invoices arrive.
SFTP drop or cloud-folder connectors: S3 events, Drive, SharePoint.
GraphQL: rarely used for intake because file uploads are awkward in it. If you want it, add it later for reading and querying, not for sending documents.
What a well-built intake does

Fast, durable acknowledgement: it returns 202 Accepted with a document ID and a status URL, and does the work asynchronously.
Idempotency: an Idempotency-Key header, so a retried upload doesn’t create two documents.
Client reference: the sender’s own external_id and free-form metadata come back on the results, so they can match the output to their record.
Completion callback: the sender registers a callback or polls the status URL.
Keys: shown once, stored hashed, with a visible prefix for support and a test/live distinction. They have scopes (upload only, read only), expiry, rotation with an overlap period, optional IP allowlist, and last-used tracking. Enterprise customers often want OAuth2 client credentials or mutual TLS instead.
Limits: per-key rate limits and quotas that return 429 with Retry-After, plus fairness so one tenant can’t starve the others.
File safety: check the real file type by its bytes (not the name), enforce size limits, scan for malware before processing, and store files under a per-tenant path.
Isolation: database row-level security or an equivalent, per-tenant encryption keys for storage, secrets in a vault, and an audit log of every intake call.
Publishing output to ERPs and other systems
Reliable delivery. The standard pattern is a transactional outbox. The result and the “send this” event are written in the same database transaction, and a relay delivers it afterwards. Delivery is at-least-once, so receivers de-duplicate by event ID. You already use this pattern for the agent’s events.

A destination is three things

A connection: credentials in a vault, with OAuth tokens refreshed automatically.
A mapping: your template fields to the target’s schema, with transforms (formats, lookups, defaults). Mapping is the real work in ERP integration.
A policy: what triggers it (committed only, or approved by a person), batching, and what to do on failure.
Delivery rules

Exponential backoff with jitter for hours or days, then a dead-letter queue with one-click replay.
Per-destination rate limits and a circuit breaker that pauses a failing endpoint.
Idempotent upserts into the ERP, keyed by your document ID or the sender’s external_id.
Store the ERP’s returned ID so each document links to its record there.
A delivery log per destination, and a reconciliation view showing sent, acknowledged and failed.
Webhooks: the signature covers the timestamp and body so replays can be rejected, secret rotation signs with both secrets for a while, and the SSRF guard blocks private addresses.

Connectors: the big platforms build native connectors for the top few systems (for you maybe QuickBooks, Xero, NetSuite, SAP, Dynamics, Odoo). For everything else they offer a generic webhook or REST destination, plus listings in Zapier, Make and n8n, so customers can reach the long tail without you writing each one. For invoices, e-invoicing standards (PEPPOL/UBL) and EDI via partners matter in some regions.

Gaps

No per-key rate limits or quotas: nothing separates upload-only from read keys.
Webhooks are single-attempt: no retry or backoff, no dead-letter or replay, no auto-disable of a broken endpoint, and no secret rotation overlap.
No destinations or mapping layer: the only output is a raw event POST, so there are no ERP connectors, no field mapping, and no ERP-returned IDs stored.
No other intake channels: no email-in, SFTP, presigned large-file upload or sandbox/test keys.
